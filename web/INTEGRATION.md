# 웹 ↔ 파일 라이프사이클 에이전트 연결 계약 초안

## 경계

1. **Mac 수집기**가 허용된 로컬 폴더의 새 파일을 발견하고 원본을 보존합니다. 브라우저는 기기 파일을 직접 감시하지 않습니다.
2. **에이전트**가 파일을 읽고 폴더 지침/프로필과 비교해 후보, 근거, 보류 이유와 계획을 만듭니다.
3. **Django API**가 사용자별 파일 메타데이터, 질문, 승인 상태와 처리 기록을 보관합니다. 브라우저는 인증된 API에서 이 데이터만 읽고 결정을 제출합니다.
4. **로컬 실행기**가 승인된 계획을 다시 검증한 뒤 이동·보관을 실행하고 저널 결과를 API에 보고합니다. 다른 사용자 요청이나 브라우저 입력을 파일 경로/쉘 명령으로 직접 실행하지 않습니다.

## 현재 API와 연결할 화면

| 화면 | 현재 API | 연결 시 필요한 항목 |
| --- | --- | --- |
| 대시보드·모든 파일 | `GET /api/v1/files/` | 실제 처리 시각, 작업 상태, 원본 기기, 미리보기 제공 권한 |
| 폴더·지침 | `GET/POST/PATCH /api/v1/folders/` | `instructions_md`를 로컬 `_project.md`/프로필과 동기화하고 버전 충돌 처리 |
| 분류 대기 | `GET /api/v1/reviews/`, `POST .../answer/` | 파일별 후보·근거·계획 조회, 승인/거절, 새 폴더 생성 미리보기 |
| 삭제 관리 | 없음 | 삭제 예정/완료 상태, 유예일, 사유, 저널 조회와 되돌리기 요청 |
| 연결·설정 | `GET /api/v1/devices/` 일부 | 기기 등록·인증, 마지막 동기화, 스크린샷 방식·질문 주기·유예 기간 |

`answer/`는 현재 답변 텍스트만 저장하며 분류나 이동을 실행하지 않습니다. 프런트엔드의 `localStorage` 결정도 API에 전달되지 않습니다. 연결 시 데모 상태와 실제 데이터 모드를 명확히 분리합니다.

## 승인 실행에 필요한 데이터

- 파일 식별자와 소유자, 원본 경로를 공개하지 않는 표시용 메타데이터
- 원본 해시 및 계획 버전, 대상 폴더/작업, 근거와 보류 사유
- 사용자 결정의 고유 요청 ID, 승인 시각, 승인자, 실행 상태
- 실행 결과의 저널 ID, 이전/이후 상태, 오류와 되돌리기 가능 여부

에이전트 `Lifecycle.execute`는 계획 재검증, 해시 확인, 대상 충돌 검사, 저널 기록을 이미 갖고 있습니다. 웹 연결은 이 검사를 우회하지 않고, 중복 요청에도 같은 작업이 두 번 실행되지 않도록 요청 ID를 사용해야 합니다. 삭제는 현재 실행기 계약과 별도로 정책·보관 위치·유예 기간을 확정한 뒤 구현합니다.

## 연결 전 확인

- HTTPS 주소와 로그인/CSRF, 소유자별 조회·변경 권한
- Mac 수집기의 인증 및 허용 경로, 원본 보존·복구 방식
- 지침 충돌과 파일 변경 후 재승인 처리
- UI의 실제 연결 상태와 데모 상태 구분
